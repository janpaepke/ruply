# Research: private helper types in library .d.ts vs. consumer declaration emit

Report of a research agent, 2026-09-21. Everything marked **[verified]** was checked against a primary source (issue/PR text via the GitHub API, published files on unpkg, or a local tsc run). **[inferred]** = the agent's reading of the evidence, not stated by anyone authoritative.

## 0. TL;DR

- There is **no compiler option or emit mechanism** that lets a library keep a helper alias unexported yet have consumers' declaration emit reference it by name. The emitter's rule is "use the alias name only when its symbol is accessible from the emitting file, otherwise expand structurally (type aliases) or error (interfaces/classes/unique symbols)". This was declared Working-as-Intended in 2016 and every proposal to change it is open/declined/unmerged (details in §1). `isolatedDeclarations` (5.5) does not change this; it moves the burden onto the consumer to annotate, and the annotation still needs a nameable type.
- Expansion of a private helper is **not just big, it is silently lossy**: the node builder replaces re-entered/deep (>10) types with `/*elided*/ any` and emits no diagnostic. Reproduced on TS 4.9.3, 5.9.3 and 7.0.2 (§3). TS7056 only fires once the serialized type exceeds ~1,000,000 length units.
- Every heavy-inference library inspected ends up exporting its helpers, either flat (rxjs, drizzle, superstruct via `export *`, RTK after a dedicated fix), under a namespace (zod v3 `objectUtil`/`util`, zod v4 `core.util`, effect `Types`), or under a "do not import" subpath (tRPC `@trpc/server/unstable-core-do-not-import`, whose source header literally says it exists to prevent "cannot be named"). Bundled-d.ts libraries (RTK, TanStack Query, valibot) still ship 40-135 module-private types each, i.e. they accept the limitation for whatever is not reached by inference.
- Practical bounding techniques that actually work without exporting: (a) consumers annotate with `ReturnType<typeof libFn<T>>` (instantiation expressions, TS 4.7+), always nameable; (b) library annotates concrete public results with lib types / exported interfaces. Two things that do **not** work: re-exporting a private alias through a public wrapper alias (`export type Public<T> = Private<T>` — emit still names the inner alias and expands), and the `{...} & {}` Prettify pattern (alias lost even when exported, because the intersection is reduced).

**Net recommendation from the team [verified across the above]:** annotate explicitly, or export whatever the inferred public types reach. `isolatedDeclarations` codifies the first half (exports must be annotated) and does not help the consumer name your private helper; `stripInternal`/`@internal` makes the situation strictly worse (a stripped declaration is unnameable *and* the compiler does not validate the result).

Pattern: nobody has found a way to keep helpers private *and* nameable. Choices are (1) export flat, (2) export under a namespace (`objectUtil`, `core.util`, `Types`, `internal`), (3) export under a "do not import" subpath (tRPC), (4) accept expansion for helpers that only appear resolved in concrete types (bundled-d.ts libraries).

## 3. Emitter behaviour and techniques — local experiment

Setup: simulated `node_modules/lib/index.d.ts` with module-private `type Rec<T>` (recursive conditional), `interface Box<T>`, `type Pretty<T> = {…} & {}`, `type Cond<T>`, `type Wrapped<T> = { inner: Rec<T> }`, `export type PublicRec<T> = Rec<T>`; a second `lib-exported` with the same helpers exported (flat and under `namespace internal`). Consumer compiled with `declaration: true` on **TS 4.9.3, 5.9.3 and 7.0.2** (native tsc). Results were identical on all three except cosmetic (`/*elided*/` comment absent in 4.9).

| Case | Emitted | Verdict |
|---|---|---|
| Private **interface** in inferred type (`export const b = makeBox(1)`, `wrapBox<T>`) | `error TS4023: Exported variable 'b' has or is using name 'Box' from external module ".../lib/index" but cannot be named` / `TS4058` for the function; **no d.ts emitted at all** | **[verified]** interface vs alias matters: interfaces/classes/unique symbols are hard errors; aliases are silently expanded. This is why RTK/xstate converted interfaces to aliases. |
| Private alias, generic wrapper `wrapRec<T>` | `T extends [infer H, ...infer R] ? { head: H; tail: R extends [infer H, ...infer R] ? /*elided*/ any : { end: true } } : { end: true }` | **[verified] silently lossy**: the recursive self-reference becomes `any` at depth 1, no diagnostic. |
| Private alias, concrete 12-deep `makeRec(1..12)` | nested object 11 levels, then `tail: /*elided*/ any` | **[verified]** depth cap. Source: `if (depth > 10) return createElidedInformationPlaceholder(context)` (`symbolDepth` in the node builder) and `visitedTypes.has(typeId) → getTypeAliasForTypeLiteral(type) ? symbolToTypeNode(alias) : createElidedInformationPlaceholder` — i.e. an *accessible* alias is what prevents the `any`. Same result with the exported helper for concrete values (see next row). |
| **Exported** alias, generic wrapper | `import("lib-exported").Rec<T>` / `import("lib-exported").internal.NsRec<T>` / nested twice `{ a: import(...).Rec<T>; b: import(...).Rec<T> }` | **[verified]** compact and exact; namespace export works as well as flat. |
| Exported alias, **concrete** value `makeRec(1,"a",true)` | still expanded structurally (`{ head: number; tail: { head: string; … } }`), deep case still `/*elided*/ any` at 11 | **[verified]** exporting only helps *deferred/generic* positions; a resolved conditional loses the alias. Bound concrete public results with an explicit named type if you need them compact. |
| Public wrapper alias over private helper: `export type PublicRec<T> = Rec<T>`, `makePublicRec(): PublicRec<T>` | expanded exactly like the private case | **[verified]** re-exporting through an alias-of-an-alias does **not** work; the type carries the innermost alias symbol (`Rec`). The helper itself must be exported (or the public alias must have its own structural body). |
| `Pretty<T> = { [K in keyof T]: T[K] } & {}` exported | `{ [K in keyof T]: T[K]; }` — alias name dropped, `& {}` gone | **[verified output; cause inferred]**: intersection reduction removes `{}` and the resulting mapped type has no alias symbol. The popular Simplify/Prettify pattern is never preserved in emit. |
| Consumer annotation `wrapRec2<T>(...): ReturnType<typeof makeRec<T>>` | `ReturnType<typeof makeRec<T>>` verbatim, with `import { makeRec } from "lib"` kept | **[verified]** always nameable, independent of the library's exports (needs TS ≥ 4.7 on the consumer side — instantiation expressions). This is the cleanest consumer-side escape hatch. |
| TS7056 threshold | `noTruncationMaximumTruncationLength = 1e6` (approximate length units, TS 5.9.3 `checker`); when exceeded under `NoTruncation` (declaration emit) → `reportTruncationError` → TS7056 and no d.ts | **[verified in source]** |

Other techniques from the field:
- **Explicit named recursive type + annotated factory** (ahejlsberg in #43817; lorefnon's zod post: cast sub-schemas to an exported `interface IDepartmentRT extends z.ZodType<…> {}` so the parent's serialized type "will refer to IDepartmentRT"). Works because interfaces are nominal-ish anchors the emitter must reference by name — but *only if exported*, otherwise TS4023 (row 1). [verified sources; mechanism verified]
- **Lib types as anchors** (`ReturnType`, `Awaited`, `Parameters`): always accessible, so `ReturnType<typeof fn<T>>` in a return-type annotation is nameable. Only helps when someone writes the annotation; the emitter never synthesizes such forms itself (#44045 open). [verified]
- **Named marker types instead of inline computed-key objects** (xstate): converting `{ readonly [uniqueSym]: true }` literals into exported aliases so emit references the alias instead of unfolding the unique symbols. [verified PR description]
- **"Mention nested results once" / lookup-table indexed access instead of nested conditionals**: no library or TS-team statement found about this; the agent's experiment shows the size problem is mainly re-entry of the *same* type (elided to `any`) and depth (>10), not the number of conditional branches. Restructuring helps only in that a non-recursive helper gets expanded exactly (no `any`), but each generic use site still carries a full copy. [inferred; ruply's own measurements in README.md show the restructuring is what bounds the size for this library]
- **api-extractor / dts bundling**: TS docs point to api-extractor for visibility control, but a rolled-up d.ts still cannot make a private type nameable — RTK's rollup helped their TS2742 (path portability) only because it removed cross-file references; they still had to export the internals. [verified from RTK PR + TS docs]

## 4. Bottom line for a library author

1. If an inferred public type can reach a helper, the helper must be **exported and reachable from a public entrypoint** (namespace export is fine and keeps the top-level surface tidy; tRPC's "do-not-import" subpath is the honest version of this).
2. Keep helpers as `type` aliases, not `interface`s, unless you export them — private interfaces turn a silent expansion into a hard TS4023 for every consumer with `declaration: true`.
3. Don't count on a wrapper alias or `& {}`-style Prettify to carry the name; both lose it in emit.
4. Tell consumers about `ReturnType<typeof fn<T>>` as the annotation form; it is the only way they can bound emit without you exporting anything, and it is what `isolatedDeclarations` will force them to write anyway.
5. Nothing on the TS roadmap changes this: the inline-alias PR is closed, alias synthesis is an open idea, TS 7 (Go) reproduces the same emit byte-for-byte.
